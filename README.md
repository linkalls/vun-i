# vun-i

Ultra-fast experimental package installer in V, aiming to mimic Bun's isolated install layout closely enough that Bun can use the result.

## What it is

`vun-i` is a prototype installer built to explore this idea:

- keep `bun install`-compatible enough for real Bun workflows
- use V for a very small, hackable installer core
- lean on hardlinks / symlinks / junctions to reduce file duplication
- target Windows NTFS pain points where install performance often hurts the most

Current design goal:

- `vun-i` installs dependencies into a **Bun-like isolated store layout**
- then delegates lockfile generation to **Bun itself** via:

```bash
bun install --lockfile-only
```

So the intended workflow is:

1. `vun-i` creates `node_modules` / `.bun` structure quickly
2. Bun generates a real `bun.lock`
3. `bun dev`, `bun run`, etc. can continue to work on top of that

## Current Bun-compatibility status

### Implemented

- Reads `package.json` dependencies
- Resolves npm registry versions with a lightweight semver matcher
- Downloads and extracts tarballs into Bun's cache directory shape
  - default: `~/.bun/install/cache`
- Creates a Bun-like isolated install store:
  - `node_modules/.bun/<store-key>/node_modules/<package>`
- Creates root links such as:
  - `node_modules/react-dom -> .bun/react-dom@18.3.1.../node_modules/react-dom`
- Creates hidden store root links under:
  - `node_modules/.bun/node_modules/*`
- Handles some self-name collision cases using nested `node_modules/node_modules/<name>` escapes
- Hydrates package metadata from cached `package.json`
  - fills in `peerDependencies`
  - fills in `bin`
- Adds peer-aware store keys
  - currently `pkg@version+<peer-hash-like-suffix>`
- Generates:
  - root `node_modules/.bin`
  - per-package `node_modules/.bin` in the store
- Windows fallback behavior:
  - tries symlink first
  - then junction (`mklink /J`) for directories
  - then hardlink / copy fallback
- Delegates `bun.lock` generation to Bun

### Partially implemented

- `peerDependencies`
  - basic peer-aware branching exists
  - not full Bun parity yet
- semver
  - supports basic cases like `^`, `~`, `<`, `>`, `<=`, `>=`, `||`
  - still far from Bun/npm-grade resolution behavior

### Not yet Bun-equivalent

- Bun's exact peer hash algorithm
- full peer conflict resolution behavior
- optional / unmet peer handling parity
- hoist decisions matching Bun exactly
- full `.bin` parity for all package.json forms and edge cases
- workspace / folder / symlink / git / tarball dependency parity
- native bin / platform-conditional package behavior parity
- exact Windows symlink/junction semantics used by Bun internally

Short version:

> The project is now fairly close in **store layout** and **link topology**, but not yet fully equal in **resolution semantics**.

## Example layout

`vun-i` currently aims for structures like:

```txt
node_modules/
  react-dom -> .bun/react-dom@18.3.1+<hash>/node_modules/react-dom
  .bin/
  .bun/
    node_modules/
      react-dom -> ../react-dom@18.3.1+<hash>/node_modules/react-dom
    react-dom@18.3.1+<hash>/
      node_modules/
        react-dom/
        scheduler -> ../../scheduler@0.23.2/node_modules/scheduler
        .bin/
```

## Usage

### Build

```bash
v -prod -o vun.exe vun.v
```

On Unix-like systems:

```bash
v -prod -o vun vun.v
```

### Run

Inside a project directory with a `package.json`:

```bash
./vun
```

or on Windows:

```powershell
.\vun.exe
```

What it does:

1. resolves dependencies from npm registry
2. downloads/extracts package tarballs
3. builds Bun-like isolated store layout in `node_modules/.bun`
4. links root packages and bins
5. runs:

```bash
bun install --lockfile-only
```

---

## Why not generate bun.lock directly?

Because Bun's text lockfile is generated by Bun's own installer/lockfile code.
Trying to fake it externally is fragile.

So `vun-i` intentionally lets Bun create the final `bun.lock`.
That keeps lockfile format correctness anchored to Bun itself.

## Bun source areas this project is following

This prototype was shaped by reading Bun's install implementation, especially:

- `src/install/isolated_install.zig`
- `src/install/isolated_install/Store.zig`
- `src/install/isolated_install/Installer.zig`
- `src/install/isolated_install/Hardlinker.zig`
- `src/install/isolated_install/Symlinker.zig`
- `src/install/lockfile/bun.lock.zig`

The current goal is not vague inspiration.
It's to get progressively closer to Bun's actual isolated install behavior.

## Caveat

This is still an experiment.

If you want production-safe installs today, use Bun.
